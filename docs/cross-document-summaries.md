# 一层跨文档摘要与单 Agent 渐进式披露

日期：2026-09-13。

## 已确定的行为

保留一个 premium QA Agent，负责检索、判断证据缺口、改写查询、继续查证和最终回答。默认和 CLI 均不创建子 Agent；旧 Python 显式子任务选项仅保留兼容性。

借鉴 [Ψ-RAG 第 3.2 节](https://arxiv.org/pdf/2605.00529) 的迭代检索与回答思路。当前实现只有一层跨文档摘要，使用已有链接和 BM25 提议候选组合，再由模型判断是否有总结价值；没有复现论文的向量聚类、merging/collapse 或多层树搜索算法。

## 摘要如何产生

文档批次完成后，`build_summaries.py` 从知识页的受控事实块选择材料。候选叶节点必须是带准确原文引用的事实或关系，不能是旧页面自由文本、已有摘要或被明确 supersedes 的事实。显式冲突保留在输入中。

第一版提议跨目录的页面对，每个种子页最多提出三个相关候选；模型可以拒绝没有共同主题或有效关联的组合。存储接口支持 2..4 个知识页，但不会生成第二层摘要。每个摘要至少涉及两个不同原始来源身份；同一来源的不同页面副本不能满足这个要求。

每页最多提供八条完整事实，每组输入事实预算为 32,000 字符。不截断单条事实或引文。摘要最多八条陈述、总正文最多 4,000 字符，明确标为“选定事实的总结”，不声称覆盖全文。

模型返回短标题和陈述；每条陈述注明 direct 或 synthesis，并指向输入事实 ID。工具从这些事实推导原文引用，不允许模型另造来源。标题只用于导航，不作为事实证据。

结果保存在 `summaries/<child-path-hash>.md`。每个摘要记录：

- 叶页面路径及内容版本。
- 陈述 ID、正文、直接陈述/综合推导类型。
- 每条陈述所依赖的页面、事实 ID、原文版本和引用位置。
- 生成时已知的相关来源版本集合，以及选取范围说明。

## QA 如何逐步展开

```text
wiki_tree
  → wiki_search(layer="summaries")
  → summary_read(view="overview")：概览与子页面
  → summary_read(view="claims")：陈述及其事实关联
  → summary_read(view="evidence", claim_ids=[一个 ID])：事实与引用
  → source_read：核验原文及必要上下文
  → 判断证据是否齐全；改写查询继续检索，或 finish_answer
```

这是根据问题选择的探索路径，不是强制执行全部步骤。人物、日期等细节问题可以直接用 `layer="details"` 或 `entity_lookup`。没有可用摘要时仍正常检索旧知识页和原文。知识页还会暴露 `related_summaries`，支持从细节回到概览。

概览和陈述映射不自动附带原文引文。展开证据时一次只接受一个陈述，避免把整个摘要对应的材料一次性塞入上下文。读取摘要不会被算作读过原文。

最终回答可包含 `summary_refs: [{path, revision, claim_ids}]`，同时保留原始 `citations`。校验器要求：引用的摘要陈述已经展开、摘要仍有效、其全部支撑引文被最终原文引用覆盖，并且这些原文区间确实读过。缺少其中一跳的引文会被拒绝。

## 更新和失败处理

知识页变化或消失、相关来源版本集合变化、原文完整性检查失败，都会使摘要过期。检索过滤过期摘要；直接读取只返回过期状态与子页面导航，不返回旧摘要正文。最终回答还会再检查一次摘要版本与状态。

重新运行构建会优先检查已有组合并重建过期摘要。提交时复核依赖版本，拒绝使用生成期间已变化的材料。被替换的摘要保存在 `.summary-history/`。

`current` 仅表示依赖未发生变化，不表示内容已被人工核验，也不表示其中引用的是某来源的最新事实。新来源进入系统后，仍需通过文档构建更新事实。来源版本不是事件发生时间，系统不会用文件时间推断哪个陈述更正确。

生成失败不把摘要缓存为成功。无关组合的跳过决定会缓存，输入变化或 `--force` 后重新尝试。每批最多 `SUMMARY_BUILD_LIMIT` 次摘要模型调用，默认 20；达到预算后记录 pending。摘要失败与已完成的文档分别报告，不撤销已验证的文档增量。批次最后的摘要统计写入 `.build/summary-last-run.json`。

## 运行

先检查当前语料是否具备来源事实：

```bash
python -m llm_wiki_bench.build_summaries \
  --wiki-dir wiki_output/hotpotqa/wiki --dry-run
```

如果没有受控事实页，需要配置现有模型后，通过新的文档构建入口重建。可先限定小批次：

```bash
python -m llm_wiki_bench.bench_ingest --dataset hotpotqa --limit 50
```

摘要阶段会自动运行。继续生成剩余摘要或重建过期摘要：

```bash
python -m llm_wiki_bench.build_summaries \
  --wiki-dir wiki_output/hotpotqa/wiki --limit 20 \
  --output results/hotpotqa/summary-build.json
python -m llm_wiki_bench.run_qa --dataset hotpotqa --limit 50 --evaluate
```

设置 `SUMMARY_BUILD_LIMIT=0` 可跳过批次后的摘要阶段。单独命令支持 `--force`、`--model` 和 `--output`；`--dry-run` 不调用模型、不生成摘要文件。

## 验证与剩余边界

- 38 项离线回归测试通过，包括旧功能的 23 项测试和新增 15 项摘要测试。
- 脚本模型走通单 Agent 的摘要检索、按陈述展开、原文回查、缺失第二跳被拒绝、补充证据后回答。
- 覆盖同源副本拒绝、递归摘要拒绝、伪造支持拒绝、原文篡改、过期/缺失依赖、生成期间修改、缓存与重试、历史保留、多陈述选择、损坏摘要不影响细节搜索及自动批次接入。
- 对现有 HotpotQA Wiki 的 dry-run：eligible_pages=0、candidate_groups=0、模型调用=0。现有旧页面尚未重建为受控事实，未自动把旧文本升级为摘要证据。
- 当前环境未配置 `OPENAI_API_KEY` 或自定义 `OPENAI_BASE_URL`，未执行真实模型构建和 QA，不声称准确率或成本改善。

事实引用与版本检查仍不能证明语义蕴含。模型可能概括错误或漏掉重要限定条件；需要真实模型抽样核验和问答评估。词汇候选也可能漏掉用词不同的相关内容。当前只是第一层摘要基线；后续应分别比较摘要覆盖、引用支持程度、完整多跳证据、答案 EM/F1、耗时和 token。上下文仍会随已读工具结果增长，渐进式披露没有替代全局上下文预算管理。
